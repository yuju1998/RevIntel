# RevIntel API

Interactive documentation is served by FastAPI at `/docs` (Swagger UI) and `/redoc`;
the OpenAPI schema is at `/openapi.json`.

## Conventions

- Business endpoints are versioned under `/api/v1`.
- Infrastructure probes (`/health`, `/ready`) are served at the root so load balancers
  and ECS health checks do not depend on API versioning.

## Running locally

```bash
source ~/.virtualenvs/revintel/bin/activate
docker compose up -d                       # PostgreSQL + Redis
cp .env.example .env                       # first time only
alembic upgrade head                       # creates lead_predictions on a fresh database
PYTHONPATH=. fastapi dev backend/app/main.py
```

`PYTHONPATH=.` puts the repo root on the path: the API imports the shared `ml` package
(feature computation and the model contract) for lead scoring, and needs the ML
dependencies from `requirements/ml.txt`. Scoring also needs the MLflow server
(`scripts/start_mlflow.sh`, see `docs/MLFLOW.md`).

## Configuration

Settings are loaded from environment variables, falling back to `.env`
(see `backend/app/core/config.py`). Unknown keys are ignored.

The API needs every required variable below. Alembic only needs `DATABASE_URL` and the
`DB_*` settings (see `docs/DATABASE.md`).

| Variable | Required | Default | Notes |
|---|---|---|---|
| `APP_NAME` | no | `RevIntel` | |
| `ENVIRONMENT` | no | `local` | One of `local`, `test`, `staging`, `production`. `local` logs human-readable lines; all others log JSON. |
| `LOG_LEVEL` | no | `INFO` | `DEBUG`, `INFO`, `WARNING` or `ERROR`. |
| `DATABASE_URL` | yes | — | Must use `postgresql+psycopg://` (explicit psycopg 3 driver) and include a database name. |
| `DB_POOL_SIZE` | no | `5` | |
| `DB_MAX_OVERFLOW` | no | `10` | |
| `DB_POOL_TIMEOUT_SECONDS` | no | `10` | Max wait for a pooled connection. |
| `DB_CONNECT_TIMEOUT_SECONDS` | no | `3` | libpq connect timeout (integer seconds). |
| `REDIS_URL` | yes | — | `redis://` or `rediss://`. |
| `REDIS_SOCKET_TIMEOUT_SECONDS` | no | `2` | Applies to connect and to commands (readiness client). |
| `CACHE_REDIS_TIMEOUT_SECONDS` | no | `0.2` | Socket timeout of the separate cache client (0 < x ≤ 5), so a slow Redis cannot stall requests. |
| `ACCOUNT_CACHE_TTL_SECONDS` | no | `300` | Lifetime of cached `GET /accounts/{id}` responses (0–86400). `0` disables caching. |
| `JWT_SECRET` | yes | — | Signing key for access tokens; at least 32 characters. Never commit or log it. |
| `JWT_ALGORITHM` | no | `HS256` | Fixed to `HS256` in V1; any other value is rejected. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | no | `60` | 1–1440. |
| `MLFLOW_TRACKING_URI` | no | `http://127.0.0.1:5001` | MLflow server used to resolve and load the `champion` model for lead scoring. |
| `MLFLOW_MODEL_NAME` | no | `revintel-lead-conversion` | Registered model whose `champion` alias is scored. |

Invalid or missing required settings stop the application at startup. Validation errors
do not echo the offending values, so connection strings do not end up in logs.

## Endpoints

### `GET /health`

Liveness probe. Returns `200` while the API process can serve requests. It never
contacts PostgreSQL or Redis, so a dependency outage does not cause the container
to be restarted.

**200 OK**

```json
{"status": "ok"}
```

### `GET /ready`

Readiness probe. Runs `SELECT 1` against PostgreSQL and `PING` against Redis.

- `200 OK` when both checks succeed.
- `503 Service Unavailable` when either check fails or times out.

The body always has the same shape. Failures are reported only as `"error"`;
connection strings, credentials and exception messages are never returned.

**200 OK**

```json
{
  "status": "ready",
  "checks": {
    "postgres": {"status": "ok", "latency_ms": 2.4},
    "redis": {"status": "ok", "latency_ms": 0.8}
  }
}
```

**503 Service Unavailable**

```json
{
  "status": "not_ready",
  "checks": {
    "postgres": {"status": "error", "latency_ms": 3001.7},
    "redis": {"status": "ok", "latency_ms": 0.9}
  }
}
```

| Field | Type | Description |
|---|---|---|
| `status` | `"ready"` \| `"not_ready"` | Overall readiness. |
| `checks.<name>.status` | `"ok"` \| `"error"` | Result of an individual dependency check. |
| `checks.<name>.latency_ms` | number | Time spent on the check, in milliseconds. |

## Request IDs and logging

- Every response carries an `X-Request-ID` header (a UUID4 generated by the server). An
  incoming `X-Request-ID` is ignored. Include it when reporting a problem; it identifies
  the request's log lines.
- Each request produces one access-log event, `http_request`, with `request_id`,
  `method`, `path` (never the query string), `route` (matched template, e.g.
  `/api/v1/accounts/{account_id}`; absent when no route matched), `status_code`,
  `duration_ms`, and `user_id` for authenticated requests. `/health` and `/ready` are
  logged at `DEBUG`.
- Every log line written while handling a request (services, repositories, libraries)
  includes the same `request_id`.
- Format: `ENVIRONMENT=local` writes human-readable lines; any other environment writes
  one JSON object per line to stdout (for CloudWatch).
- Logs never contain passwords, password hashes, tokens, `Authorization` headers, the JWT
  secret or database/Redis credentials. Sensitive keys are redacted, and JWTs, bearer
  tokens, Argon2 hashes and URL credentials are scrubbed from any message. Uvicorn's own
  access log is disabled; SQLAlchemy statement and httpx request logging stay at `WARNING`
  regardless of `LOG_LEVEL`.
- Unhandled errors return `500 {"detail": "Internal Server Error"}` with `X-Request-ID`.
  The error is logged once as `unhandled_exception` with `exception_type` and the stack
  frames (file, line, function). The exception message, source lines and local variables
  are never logged or returned.

## Authentication

Stateless JWT bearer authentication. There is no signup, refresh token, password reset or
SSO in V1.

- **Protected:** every CRM mutation (`POST /accounts`, `POST /contacts`, `POST /leads`,
  `POST /opportunities`, `PATCH /opportunities/{id}`, `POST /activities`, `POST /notes`)
  and `GET /users/me`.
- **Public:** `POST /auth/login`, `/health`, `/ready`, and all CRM `GET` endpoints.
- Send the token as `Authorization: Bearer <access_token>`. In Swagger UI (`/docs`), use
  **Authorize** and paste the token.
- Missing, malformed, expired or otherwise invalid tokens, and tokens of deleted or
  **inactive** users, return `401` with `WWW-Authenticate: Bearer` and
  `{"detail": "Could not validate credentials"}`. Authentication is checked before the
  request body, so an unauthenticated request with an invalid body gets `401`, not `422`.
- The user's role and active flag are read from the database on every request; they are
  not taken from the token. Deactivating a user blocks their existing tokens immediately.
- Roles: `ADMIN` and `SALES_REP` currently have the same permissions. Insufficient role,
  where a future endpoint requires one, returns `403 {"detail": "Insufficient permissions"}`.

### `POST /api/v1/auth/login` → `200`

```json
{"email": "rep@example.com", "password": "..."}
```

The email is matched case-insensitively (trimmed and lowercased). Response:

```json
{"access_token": "eyJ...", "token_type": "bearer", "expires_in": 3600}
```

Access tokens are HS256 JWTs that expire after `ACCESS_TOKEN_EXPIRE_MINUTES` (60). Claims:
`sub` (user id), `iat`, `exp`, `iss` = `revintel`, `aud` = `revintel-api`,
`type` = `access`. No role, email or status is stored in the token.

Unknown email, wrong password and inactive user all return the same
`401 {"detail": "Incorrect email or password"}`. Malformed login bodies return `422`;
unlike other endpoints, these validation errors never include the submitted input, so the
password is never echoed back.

### `GET /api/v1/users/me` → `200`

The authenticated user (never includes the password hash):

```json
{"id": "...", "email": "rep@example.com", "full_name": "Sales Rep", "role": "SALES_REP",
 "is_active": true, "created_at": "...", "updated_at": "..."}
```

### Creating users

There is no user API. Create users with the CLI from the repository root (needs only
`DATABASE_URL`); it uses the same service as the application (email lowercased, Argon2
hash, duplicate emails rejected case-insensitively):

```bash
PYTHONPATH=backend python -m app.cli.create_user \
    --email admin@example.com --full-name "Ada Admin" --role ADMIN
# prompts for the password twice (12-1024 characters); for scripts:
printf '%s\n' "$PASSWORD" | PYTHONPATH=backend python -m app.cli.create_user ... --password-stdin
```

Never pass passwords as command-line arguments (they end up in shell history and process
lists).

## CRM API conventions (`/api/v1`)

Mutations require a bearer token (see [Authentication](#authentication)); reads are public.

### Errors

| Situation | Status | Body |
|---|---|---|
| Malformed JSON, wrong types, failed field validation, unknown fields, malformed UUID | `422` | FastAPI validation error: `{"detail": [{"loc": [...], "msg": "...", ...}]}` |
| Valid UUID in the **path** that does not exist | `404` | `{"detail": "Account <id> not found"}` |
| Valid UUID in the **body** referring to a nonexistent record (e.g. `account_id`, `owner_id`) | `422` | `{"detail": "account_id does not refer to an existing account"}` |
| Business rule violated (e.g. inactive owner, creating a `CONVERTED` lead, references to different accounts) | `422` | `{"detail": "owner_id refers to an inactive user"}` |
| Missing/invalid/expired token, or inactive/deleted user | `401` | `{"detail": "Could not validate credentials"}` |
| Authenticated but role not allowed (no V1 endpoint yet) | `403` | `{"detail": "Insufficient permissions"}` |
| Lead scoring cannot use the model (MLflow unreachable, no `champion`, model/feature-spec mismatch, malformed model output) | `503` | `{"detail": "Lead scoring is currently unavailable."}`; the specific reason is only logged (`lead_scoring_unavailable`) |
| Unexpected server error | `500` | `{"detail": "Internal Server Error"}` (see [Request IDs and logging](#request-ids-and-logging)) |

Request bodies reject unknown fields (`422`), so a misspelled or unsupported field is never
silently ignored.

### Data representation

- **IDs** are UUIDs.
- **Money** (`annual_revenue`, `estimated_value`, `amount`) is USD with two decimal places.
  Requests accept a JSON number or string (`1234.5` or `"1234.50"`); more than two decimal
  places, negative values, `NaN` and infinities are rejected. **Responses always return
  money as a string** (`"1234.50"`) so decimal precision is never lost to floating point.
  Clients should parse it with a decimal type.
- **Timestamps** (`created_at`, `updated_at`, `converted_at`) are ISO 8601 in UTC, e.g.
  `"2026-10-20T23:15:27.785992Z"`. `expected_close_date` is a date (`"2026-12-31"`).
- **Text** fields are trimmed; required text must be non-blank. Maximum lengths match the
  database (names 255, email 320, phone 50, website 2048).
- **Contact and lead emails** are trimmed and syntax-checked, but otherwise stored exactly
  as entered (casing preserved). They are not unique.
- **Counts** (`employee_count`, `company_size`) are integers `>= 0`.
- **`owner_id`** is optional and never defaults to the authenticated user (ownership is an
  assignment, not authorship). If given, it must refer to an existing, **active** user,
  otherwise `422`. Owners are never assigned automatically.

### Pagination

List endpoints use limit/offset pagination:

| Query parameter | Default | Constraint |
|---|---|---|
| `limit` | `50` | `1`–`100` |
| `offset` | `0` | `>= 0` |

```json
{"items": [...], "total": 3, "limit": 50, "offset": 0}
```

`total` is the number of rows **matching the filters**, not the size of the table. Items
are ordered newest first (`created_at` descending, then `id`). An offset past the end
returns an empty `items` list with the correct `total`.

### Filters

Filters are optional, use exact matching, and combine with pagination.

| Endpoint | Filters |
|---|---|
| `GET /api/v1/accounts` | `industry` (exact, case-sensitive) |
| `GET /api/v1/leads` | `status`, `lead_source` (enum values; unknown values return `422`) |
| `GET /api/v1/accounts/{id}/timeline`, `GET /api/v1/leads/{id}/activities` | none (pagination only) |

Examples: `GET /api/v1/leads?status=QUALIFIED&lead_source=WEB&limit=20&offset=20`,
`GET /api/v1/accounts?industry=Software`.

## CRM endpoints

### Accounts

#### `POST /api/v1/accounts` → `201`

| Field | Type | Required |
|---|---|---|
| `name` | string (≤255) | yes |
| `industry` | string (≤255) | no |
| `employee_count` | integer `>= 0` | no |
| `annual_revenue` | money, up to 14 digits before the decimal point | no |
| `website` | string (≤2048) | no |
| `owner_id` | UUID of an active user | no |

Account names are not unique. `422` for validation errors or an unknown/inactive owner.

```json
{
  "id": "222342a4-6a20-4ddf-ac41-e37935f2e065",
  "name": "Acme Corp",
  "industry": "Software",
  "employee_count": 250,
  "annual_revenue": "1234567.50",
  "website": null,
  "owner_id": null,
  "created_at": "2026-10-20T23:15:27.785992Z",
  "updated_at": "2026-10-20T23:15:27.785992Z"
}
```

#### `GET /api/v1/accounts` → `200`

Paginated list of accounts. Optional filter: `industry`.

#### `GET /api/v1/accounts/{account_id}` → `200`

`404` if the account does not exist; `422` for a malformed UUID.

**Caching.** Responses are cached in Redis (cache-aside) for `ACCOUNT_CACHE_TTL_SECONDS`
(default 5 minutes). The response is identical whether it comes from the cache or from
PostgreSQL.

- Key: `revintel:v1:account:{account_id}`; value: the `AccountRead` JSON shown above
  (never ORM objects or pickled data). `v1` is bumped if the response shape changes.
- `404`s are never cached.
- Redis is an optimization only: if Redis is slow, down or returns a corrupt entry, the
  account is read from PostgreSQL and the request succeeds. Failures are logged as
  `cache_unavailable` / `cache_entry_invalid` warnings (exception type only).
- There is no account update/delete API yet, so nothing invalidates entries through the
  API. Changes made directly in the database (e.g. a deleted owner being set to `null`)
  can be served stale for up to the TTL. Future account mutations must call
  `AccountCache.invalidate()` after their transaction commits.
- `/ready` still reports Redis: if Redis is down it returns `503` even though this endpoint
  keeps working. Choose the load balancer health-check target accordingly.

| Field | Type | Required |
|---|---|---|
| `account_id` | UUID of an existing account | yes |
| `first_name`, `last_name` | string (≤255) | yes |
| `email` | email (≤320), stored as entered | no |

### Leads

#### `POST /api/v1/leads` → `201`

| Field | Type | Required |
|---|---|---|
| `company_name`, `contact_name` | string (≤255) | yes |
| `lead_source` | `WEB`, `REFERRAL`, `EVENT`, `OUTBOUND`, `PARTNER`, `OTHER` | yes |
| `email` | email (≤320), stored as entered | no |
| `industry` | string (≤255) | no |
| `company_size` | integer `>= 0` | no |
| `estimated_value` | money, up to 12 digits before the decimal point | no |
| `status` | `NEW` (default), `WORKING`, `QUALIFIED`, `DISQUALIFIED` | no |
| `owner_id` | UUID of an active user | no |

`status: "CONVERTED"` returns `422`: lead conversion will be a separate workflow.
`converted_at` is not accepted (unknown field, `422`); it is returned as `null`.

#### `GET /api/v1/leads` → `200`

Paginated list of leads. Optional filters: `status`, `lead_source`.

#### `GET /api/v1/leads/{lead_id}` → `200`

`404` if the lead does not exist; `422` for a malformed UUID.

#### `POST /api/v1/leads/{lead_id}/scores` → `201`

Scores the lead now with the champion model and stores the score (no request body;
requires a bearer token). Each call adds a row; earlier scores are kept.

1. Captures one UTC prediction timestamp `T`.
2. Computes the point-in-time features at `T` with the same feature code as model training.
   Only activities with `occurred_at <= T` and `created_at <= T` count.
3. Uses the registered model's `champion` version. The alias is resolved once per API
   process and the model is cached, so restart the API after promoting a new champion.
4. Predicts the class-1 probability (`predict_proba`), assigns the tier and stores the
   score.

```json
{
  "lead_id": "6f1c...",
  "conversion_probability": 0.173,
  "lead_tier": "HOT",
  "model_name": "revintel-lead-conversion",
  "model_version": "4",
  "prediction_timestamp": "2026-11-10T07:12:03.481920Z",
  "inference_ms": 14.8
}
```

| Field | Meaning |
|---|---|
| `conversion_probability` | Probability that the lead converts in `(T, T + 30 days]`. |
| `lead_tier` | Product policy: `HOT` ≥ 0.15, `WARM` ≥ 0.05, `COLD` < 0.05. These thresholds are separate from the model's evaluation threshold. |
| `model_version` | The concrete MLflow version that produced the score. |
| `inference_ms` | Model inference time only, excluding feature computation and storage. |

**Errors:**
- `401` without a token.
- `404` if the lead does not exist.
- `503` if scoring is unavailable (see [Errors](#errors)). Nothing is stored.

#### `GET /api/v1/leads/{lead_id}/scores/latest` → `200`

The most recent stored score, in the same shape, exactly as it was stored. The tier isn't
recomputed, and neither MLflow nor the model is called. `404` with `Lead <id> not found`
if the lead doesn't exist, or `No score found for lead <id>` if it has never been scored.

### Opportunities

#### `POST /api/v1/opportunities` → `201`

| Field | Type | Required |
|---|---|---|
| `account_id` | UUID of an existing account | yes |
| `name` | string (≤255) | yes |
| `stage` | `PROSPECTING`, `QUALIFICATION`, `PROPOSAL`, `NEGOTIATION`, `CLOSED_WON`, `CLOSED_LOST` | yes |
| `amount` | money, up to 12 digits before the decimal point | no |
| `expected_close_date` | date | no |
| `description` | string | no |
| `owner_id` | UUID of an active user | no |

`422` if `account_id` does not exist or the owner is unknown/inactive.

#### `PATCH /api/v1/opportunities/{opportunity_id}` → `200`

Partial update. Updatable fields: `name`, `stage`, `amount`, `expected_close_date`,
`description`, `owner_id`.

- **Omitted fields are left unchanged.**
- `null` clears a nullable field (`amount`, `expected_close_date`, `description`,
  `owner_id`); `null` for `name` or `stage` returns `422`.
- `account_id` cannot be changed: opportunities do not move between accounts (`422`).
- Any stage may change to any other stage.
- `{}` is a no-op: `200` with the unchanged opportunity; `updated_at` does not change.
- `updated_at` advances only when a value actually changes.
- `404` if the opportunity does not exist.

### Activities

#### `POST /api/v1/activities` → `201`

| Field | Type | Required |
|---|---|---|
| `account_id`, `lead_id`, `opportunity_id`, `contact_id` | UUID | **at least one** (several allowed) |
| `activity_type` | `CALL`, `EMAIL`, `MEETING`, `DEMO`, `FOLLOW_UP` | yes |
| `direction` | `INBOUND`, `OUTBOUND`, `INTERNAL` | yes |
| `subject` | string (≤255), trimmed | no |
| `body` | string; if given must contain non-whitespace; stored exactly as submitted | no |
| `occurred_at` | timezone-aware ISO 8601 datetime, when it actually happened | yes |

Rules:

- `occurred_at` without a UTC offset is rejected (`422`), as is any value more than
  **5 minutes in the future** (`422`). Values are returned in UTC.
- Every supplied parent must exist (`422`, e.g. `"contact_id does not refer to an existing
  contact"`).
- `account_id`, the opportunity's account and the contact's account must all be the same
  account (`422`, e.g. `"account_id, contact_id refer to different accounts"`). A
  `lead_id` may be combined with any of them: leads have no account.
- **`account_id` is derived** when omitted: from the opportunity or contact. The response
  shows the stored (canonical) `account_id`. Lead-only activities keep `account_id: null`.
- **`created_by_id` is always the authenticated user.** It is not accepted in the request
  (sending it returns `422`), so clients cannot record activities as someone else.

```json
{
  "id": "4ed37f2e-dca8-4415-b45f-ba355857c175",
  "account_id": "0eb86761-b0c2-4822-8451-ea00b2ba097e",
  "lead_id": null,
  "opportunity_id": "0a6ac9fd-1898-4545-b1b3-e2af9eab2c30",
  "contact_id": null,
  "created_by_id": null,
  "activity_type": "MEETING",
  "direction": "OUTBOUND",
  "subject": "Pricing review",
  "body": null,
  "occurred_at": "2026-10-21T17:06:17.855060Z",
  "created_at": "2026-10-21T19:06:17.915919Z"
}
```

#### `GET /api/v1/leads/{lead_id}/activities` → `200`

Paginated `Page[Activity]` of activities with this `lead_id`, newest first by
`occurred_at` (ties: `id` descending). `404` if the lead does not exist (a lead without
activities returns an empty page); `422` for a malformed UUID or invalid pagination.

### Notes

#### `POST /api/v1/notes` → `201`

| Field | Type | Required |
|---|---|---|
| `account_id`, `lead_id`, `opportunity_id` | UUID | **at least one** (several allowed) |
| `body` | string; must contain non-whitespace; stored exactly as submitted | yes |

The same existence and cross-account rules as activities apply. **`author_id` is always the
authenticated user** and is not accepted in the request (`422`). `account_id` is
derived from `opportunity_id` when omitted. Notes have no `contact_id`. There is no note
update endpoint yet.

### Account timeline

#### `GET /api/v1/accounts/{account_id}/timeline` → `200`

Activities and notes for the account in one newest-first stream, with the usual
`limit`/`offset` pagination. Ordering and pagination are done by the database across
**both** record types, so pages never overlap or skip records, and `total` counts
activities + notes for the account.

Each item is an activity or a note with two extra API-only fields:

| Field | Description |
|---|---|
| `record_type` | `"activity"` or `"note"` (discriminator; the rest of the item has that record's fields) |
| `event_timestamp` | Ordering timestamp: `occurred_at` for activities, `created_at` for notes |

Order: `event_timestamp` descending, then `record_type` ascending (`activity` before
`note`), then `id` descending, so equal timestamps always appear in the same order.

Included: records whose `account_id` is this account (including records linked only via
the account's opportunities or contacts, because their `account_id` is derived). Lead-only
records (`account_id: null`) and other accounts' records never appear.

```json
{
  "items": [
    {"record_type": "note", "event_timestamp": "2026-10-21T19:06:18.008385Z",
     "id": "e76be814-...", "account_id": "0eb86761-...", "lead_id": null,
     "opportunity_id": null, "author_id": null, "body": "  Champion: CFO\n",
     "created_at": "2026-10-21T19:06:18.008385Z", "updated_at": "2026-10-21T19:06:18.008385Z"},
    {"record_type": "activity", "event_timestamp": "2026-10-21T17:06:17.855060Z",
     "id": "4ed37f2e-...", "account_id": "0eb86761-...", "activity_type": "MEETING",
     "direction": "OUTBOUND", "occurred_at": "2026-10-21T17:06:17.855060Z", "...": "..."}
  ],
  "total": 2,
  "limit": 50,
  "offset": 0
}
```

`404` if the account does not exist; `422` for a malformed UUID or invalid pagination.

## Tests

```bash
pytest                  # unit/application tests; no Docker required
pytest -m integration   # real PostgreSQL/Redis tests; requires `docker compose up -d`
```

Integration tests use `revintel_test` by default; override with `TEST_DATABASE_URL`
and `TEST_REDIS_URL`. The test database is rebuilt from the Alembic migrations at the start
of each run, and setup refuses to run unless the database name ends in `_test`
(see `docs/DATABASE.md`).
